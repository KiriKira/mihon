# 漫画页面正向显示：当前方案与后续方向

> 状态：2026-08-21 第二轮完成（聚合与几何守卫），等待扩充样本复验  
> 记录日期：2026-08-21  
> 当前实现快照：`b44704574` 之后（见文末「2026-08-21 第二轮」）

## 目标与决策原则

“强制本页正向显示”需要判断漫画页是否横倒，并在有充分把握时返回顺时针
`90°`、`180°` 或 `270°` 的修正角度。

这个功能的首要原则是保守：

- 横倒页没有转正属于漏判，仍可由用户手动处理。
- 正常页被错误旋转会直接打断阅读，代价更高。
- 无文字、证据冲突或置信度不足时必须保持 `0°`。
- 繁体中文和日文都是主要漫画文本，不能把繁体中文识别视为多余步骤。
- 不从头训练模型；优先评估已有轻量模型和可解释的组合算法。

## 当前测试语料

`test_pic/` 当前约定如下：

- `test_pic/landscape/`：17 张应当旋转的图片。
- `test_pic/portrait/`：19 张已经正向、不得旋转的图片。
- `test_pic/3.jpg` 至 `9.jpg`：7 张早期样本，保留作历史回归用例；其中有正常文字页和无文字页。

目录标签目前只表达“需要旋转/不需要旋转”，没有记录每张横倒图的正确角度是
`90°` 还是 `270°`。后续做严格方向准确率测试前，应增加独立的清单，例如 CSV：

```text
path,expected_correction,title_or_series,notes
landscape/example.jpg,90,example-series,vertical Japanese text
portrait/example.webp,0,example-series,upright spread
```

不要根据文件所在目录、文件名、作品名或卷号参与推理；这些信息只用于标注和划分
测试集。

早期 9 张样本曾得到预期结果，但用户在真实阅读中反馈效果仍不理想。新增语料尚未
运行完整基准，因此不能用早期结果证明当前方案已经可用，也不应继续围绕少量样本
手调阈值。

## 当前实现

核心代码位于：

- `app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/PageOrientationDetector.kt`
- `app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/pager/PagerPageHolder.kt`
- `app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/webtoon/WebtoonPageHolder.kt`
- `app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/pager/PagerViewer.kt`
- `app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/webtoon/WebtoonViewer.kt`

依赖为 ONNX Runtime Android，以及 ML Kit 的中文和日文文字识别模块。

### 1. 图像预处理

1. 使用 `BitmapFactory` 解码预览图，最大边目标约为 1600 像素。
2. 将短边缩放到 256 像素。
3. 大比例缩小时先反复减半，再缩到目标尺寸，以减少漫画网点产生的混叠。
4. 复用一个像素缓冲和一个 NCHW 浮点输入缓冲，避免为每个裁剪重复分配大数组。

### 2. ONNX 方向候选

当前模型是由 PaddleOCR `PP-LCNet_x1_0_doc_ori` 转换的
`page_orientation.onnx`。它原本是文档方向四分类模型，输出类别为当前图像的
`0°`、`90°`、`180°`、`270°` 朝向。

推理过程：

1. 分别把缩略图像素旋转 `0°`、`90°`、`180°`、`270°`。
2. 每个方向沿页面长轴均匀取 5 个 `224 × 224` 裁剪，共运行 20 次小模型推理。
3. 对每个像素旋转方向，只采用置信度最高的那个裁剪。
4. 最高类别置信度必须至少为 `0.80`。
5. 最高类别与第二名的差必须至少为 `0.40`。
6. 把四个像素旋转下的类别对齐回原图坐标系；四者必须完全一致。
7. 一致类别为 `0°` 时保持原图；否则取该方向的逆旋转作为候选修正角度。

这一步只产生候选，不直接决定旋转。

### 3. CJK 文字门控

只有 ONNX 给出非零候选后才运行 OCR：

1. 先运行 ML Kit 中文文字识别。
2. 若证据不足，再运行日文文字识别。
3. 识别结果中只统计 CJK 统一表意文字、平假名和片假名等相关 Unicode 区块。
4. 至少需要 6 个有效字符，并分布在至少 2 个文字 element 中。
5. 中文或日文任一达到门槛，接受 ONNX 的候选角度；否则保持 `0°`。

这里的 OCR 只证明“页面上可能有足够的中日文文字”，并没有证明这些文字在候选
方向上是正立的。

### 4. 缓存与预处理

- 结果以 `ReaderPage` 对象为弱键保存在内存中。
- 分页和条漫阅读器会尝试后台预判后续 3 张已经可用的页面。
- 当前页请求优先于后台任务；翻页时会取消旧的预判队列。
- 后台文件读取发生在获取识别互斥锁之前，避免慢 I/O 阻塞当前页识别。
- 双页拆分时不复用整页缓存，也不做后续页预判，因为不同半页不能安全共享结果。
- 变换后的页面没有稳定页键时会即时判断，不写入按页缓存。

### 5. 错误处理与日志

- 解码、读取、ONNX、OCR 或后台预判失败时均回退为 `0°`。
- 协程取消会继续向上传递，不会被当作普通错误缓存。
- 普通判断记录页码、耗时、四方向类别、OCR 证据和接受/拒绝原因。
- 异常使用 `ERROR` 并附带堆栈，不应导致阅读器闪退或页面加载失败。

ADB 过滤命令：

```bash
adb logcat | grep "Page orientation"
```

Release 版本默认记录 `INFO` 及以上；若需要完整逐页 `DEBUG` 判断，应在 Mihon 中
启用详细日志。

### 6. 历史性能观察

在此前连接的 Samsung SM-F9560 上，对早期样本观察到：

- 分类阶段拒绝的页面约 0.3 秒。
- 进入中文或日文 OCR 并接受候选的页面约 0.6–0.7 秒。
- 已缓存页面再次显示基本不需要等待。

这些只是旧样本上的粗略实机观察，不是新的 `landscape/portrait` 语料基准，也不是
性能承诺。后续需要重新测量冷启动、热启动以及连续翻页的 P50/P95。

## 已知问题

### 模型领域不匹配

`PP-LCNet_x1_0_doc_ori` 面向文档、证件等图像，并非漫画。漫画中的人物、分镜、
网点、拟声词、竖排文字和留白分布可能被模型当作方向特征。模型在四次旋转下表现
自洽，只能说明它具有旋转等变性，不能说明它抓住了正确语义。

### 单个最强裁剪可以支配整页

当前每个方向从 5 个裁剪中选最高置信度的一个。一个恰好触发错误模式的局部区域
可能压过其他四个裁剪；这是当前聚合方式最明显的风险之一。

### OCR 只验证文字存在，不验证文字朝向

ML Kit 对整页旋转具有一定鲁棒性。当前门控没有比较不同候选方向下的文字可读性，
因此“检测到 CJK 文字”不能排除正向页面被 ONNX 错判。OCR 的误识别或幻觉也可能
跨过 6 字符/2 element 的固定门槛。

### 固定阈值缺少校准

`0.80` 置信度、`0.40` margin、6 字符、2 element 均来自有限样本调试，尚未在按
作品隔离的验证集上校准。模型分数也不一定是真正可比较的概率。

### 文字与版式多样性

- 繁体中文、简体中文、日文汉字、假名、竖排文字和横排文字混杂。
- 页面可能只有拟声词、极少对白，或者完全没有文字。
- 跨页、封面、插图、故意横置的构图和真正扫描横倒在视觉上可能非常接近。
- CJK 门控会保守拒绝只有拉丁文字或没有文字的横倒页，这是当前预期行为，但会造成
  漏判。

### 评估集仍然很小

17 个正例和 19 个负例不足以代表真实漫画分布。若同一作品相邻页同时出现在调参集
和验证集，版式高度相似，会产生虚高结果。必须按作品或至少按卷分组切分，而不是
随机按图片切分。

## 下一轮建议

下面是候选方向，不代表都要实现。建议按优先级逐项做离线对比，只有明确改善留出集
指标的方案才进入 Android 阅读链路。

### 候选算法矩阵

| 方案 | 核心做法 | 手机端成本 | 适合解决的问题 | 主要限制 | 建议 |
| --- | --- | --- | --- | --- | --- |
| A. 文字感知的选择性集成 | 当前页面模型只负责提候选；文字框几何、文字行方向和裁剪一致性负责复核；证据冲突就拒判 | 中 | 降低正常页被单一错误裁剪带偏 | 需要校准多个信号，竖排日文不能用简单横竖规则 | **主推** |
| B. 文字检测 + 文字行方向模型 | 先找真实文字区域，把文字行归一化后判断 `0°/180°`，再结合文字行轴向区分四方向 | 低至中 | 文档页面模型与漫画领域不匹配 | 现成轻量模型通常只分 `0°/180°`，不能单独完成四分类 | **优先基准** |
| C. 四方向 OCR 似然比较 | 对四个候选分别 OCR，比较字符、置信度、稳定行数和几何合理性，只接受明显胜者 | 高 | 直接验证“哪个方向更可读” | 可能要跑 2–4 次 OCR；ML Kit 可能对旋转过于鲁棒，导致四向分数接近 | 离线验证后决定 |
| D. 传统文字/线条几何 | 二值化、连通域、投影轮廓、Hough/Radon 或文字框聚类，估计主文字轴 | 低 | 便宜地排除明显不合理候选 | 通常只能得到模 `180°` 的轴向，网点、分镜线和拟声词噪声很大 | 只作先验/否决器 |
| E. 校准后的选择性分类器 | 用现有 logits、裁剪一致性、OCR、版式等少量特征训练逻辑回归或浅层树，并保留 unknown | 很低 | 用统一规则替代大量手调阈值 | 当前 36 张主语料远远不够；必须按作品留出 | 样本扩充后主推 |
| F. 章节序列模型 | 用 HMM/Viterbi 或简单动态规划，让相邻页方向成为弱先验，并设高切换代价和 unknown 状态 | 很低 | 连续扫描横倒、单页证据偏弱 | 硬多数会误伤封面、跨页和特殊构图 | 后期增强，不单用 |
| G. 通用视觉语言模型 | 用 MobileCLIP 一类移动视觉特征比较四张旋转图或文字提示的得分 | 中至高 | 探索更通用的语义方向信息 | 零样本漫画方向能力没有证据，模型和运行时明显更重 | 仅桌面研究 |
| H. 人脸/人体方向 | 检测漫画人脸、眼睛或人体姿态，作为正立证据 | 中 | 文字极少但有人物的页面 | 漫画域检测器稀少；侧脸、倒置构图、无人页面都不稳定 | 低优先级否决器 |
| I. EXIF + 用户覆盖 | 先应用可靠的 EXIF 方向；允许用户对页或章节保存手动旋转 | 极低 | 元数据正确的图片，以及算法无法判断的意图问题 | 像素已经错误旋转的扫描通常没有可用 EXIF | 应作为产品兜底 |

这里的“选择性”很重要：目标不是强迫算法对每一页都给四分类答案，而是允许输出
`unknown`，在没有足够证据时保持 `0°`。应比较的是风险—覆盖率曲线：自动处理多少
页面，以及在这些已接受页面中误旋转多少，而不只是所有图片上的总准确率。

### 推荐的下一版架构

最值得先验证的不是简单更换一个大模型，而是 **A + B + E** 的组合，章节上下文 F
只处理临界样本，I 负责不可判定情况：

1. **确定性预处理**：若文件带有可信 EXIF 方向，先规范化；不要让后续模型重复修正。
2. **廉价候选生成**：保留当前四方向页面模型，但将单个最强裁剪改为中位数、截尾
   均值、top-k 一致性或多数投票，同时输出候选角度和不确定度。
3. **真实文字区域复核**：使用 ML Kit 返回的 `TextBlock/Line/Element` 边界框、角点、
   置信度和旋转信息，只分析检测到的文字区域，而不是人物和背景。ML Kit Android
   的结果对象确实暴露这些字段，见[官方结果结构说明](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)。
4. **文字行极性判断**：在归一化后的文字行上评估轻量 `0°/180°` 分类器。PaddleOCR
   的 `PP-LCNet_x0_25_textline_ori` 官方模型约 0.96 MB，但它只支持 `0°/180°`，且
   官方测试数据主要是证件和文档，不能把其公布准确率直接外推到漫画，见
   [PaddleOCR 文字行方向文档](https://www.paddleocr.ai/v3.3.1/version3.x/module_usage/textline_orientation_classification.html)。
   因此它只能和文字行轴向、候选旋转共同使用，不能单独替换当前四方向判断。
5. **校准与拒判**：把页面模型 margin、各裁剪分歧、文字框数量、文字行方向一致率、
   OCR 置信度差和页面长宽比输入一个很小的校准器。只有预计误旋转风险低于目标时
   才接受，否则返回 `0°`。
6. **章节弱先验**：仅当单页落在临界区时，参考前后已经高置信接受的页面；封面、
   跨页或单页强证据可以随时打破章节趋势。
7. **人工兜底**：保留当前手动旋转，并可考虑记住单页/章节覆盖。纯像素算法无法可靠
   区分“扫描意外横倒”和“作者故意横向构图”，这不是增加分类器就一定能解决的。

该架构仍可维持“错误只写日志并返回 `0°`，不影响页面显示”的安全边界。集成移动端
新模型前，应先在桌面复现完全相同的图像预处理和判决逻辑；PaddleOCR 也提供
[Android 端侧部署说明](https://www.paddleocr.ai/v3.0.3/en/version3.x/deployment/on_device_deployment.html)，
但是否沿用 ONNX Runtime 仍应以 Mihon 的包体、延迟和维护成本决定。

### 各方案的具体实验方式

#### B：文字行方向，不直接做整页四分类

1. 用 ML Kit 取得文字行或 element 的四角坐标。
2. 根据长轴把文字区域分成横排、竖排和不确定，不把“竖排”直接解释为“页面横倒”。
3. 对每个候选页面旋转，把文字行裁成统一方向，再运行 `0°/180°` 文字行模型。
4. 按文字面积和识别置信度加权投票；小拟声词、低置信框和极短文本降低权重。
5. 只有多个独立文字行同意，并且与页面候选一致时才接受。

这能把四方向问题拆成“文字轴向”和“沿轴正反”两个较容易的问题。早期单独试验过
`0°/180°` 文字行模型，它会被正常竖排漫画干扰，所以本轮不能再次把它直接作用于
整页。

#### C：四方向 OCR 竞争

每个方向定义一个可解释分数，例如：

```text
ocr_score =
    valid_cjk_characters
  + weighted_confidence
  + stable_text_lines
  + geometry_consistency
  - implausible_fragment_penalty
```

接受条件不是“字符超过 N 个”，而是第一名明显高于第二名，并且多个文字块支持同一
方向。必须先统计 ML Kit 四向分数是否真的有区分度；如果引擎会自动适应旋转，或四次
结果基本相同，就停止这条路线。为控制延迟，可以先只比较当前候选和 `0°`，两者接近
时直接拒判，而不是固定跑满四次。

#### D：传统几何只回答它擅长的问题

文字框的中心、长轴和间距可以通过投影轮廓、连通域聚类或 Hough/Radon 类方法估计
页面的主要排版轴。多方向文字行检测本身是成熟的研究方向，例如
[CVPR 2014 的 orientation-robust text-line detection](https://www.cv-foundation.org/openaccess/content_cvpr_2014/papers/Kang_Orientation_Robust_Text_2014_CVPR_paper.pdf)。
但这类几何通常只能判断“横轴还是竖轴”，不能可靠分辨正立与倒立，也无法知道作者
是否故意横排。因此应把它用来缩小候选或否决明显错误，不应单独决定最终旋转。

#### E：小型校准器，而不是重训视觉模型

校准器的输入是现有模块已经产生的数值，不直接吃图片。例如：

- 四方向页面 logits、第一/第二名差值和熵；
- 5 个裁剪之间的同意率、top-k 稳定性和不同尺度的一致性；
- 中文/日文 OCR 的字符、行、置信度和几何统计；
- 文字行 `0°/180°` 的加权投票；
- 页面比例、文字覆盖率、是否疑似跨页；
- 与相邻高置信页面是否一致。

先用逻辑回归作为可解释基线；若确有收益，再试浅层梯度提升树。训练目标应对正常页
误旋转赋予远高于漏判的代价，并通过阈值输出 unknown。它不属于“从头训练漫画视觉
模型”，但至少需要数百张、多个作品且标签可靠的数据，当前 36 张只适合发现问题，
不适合训练或证明泛化。

#### F：章节上下文的安全形式

可以把每页隐藏状态设为 `0/90/180/270/unknown`：单页算法提供 emission score，
相邻页切换产生小惩罚，再用 Viterbi 求最可能序列。安全约束是：

- 只有临界页能被上下文抬高，强 `0°` 证据不能被覆盖；
- `unknown` 必须是合法状态，不能强制每页跟随章节多数；
- 封面、跨页、彩图和章节边界降低或切断转移权重；
- 上下文修正仍需记录原始分数和原因，方便 ADB 回溯。

#### G/H：研究项，不应先进入 APK

[Apple MobileCLIP](https://machinelearning.apple.com/research/mobileclip) 是面向移动端的
通用图文模型，但即使较小版本也比当前专用方向分类器复杂得多，而且没有证据表明
零样本提示能稳定区分漫画扫描错误与故意构图。它最多先在桌面上作为失败样本分析器，
不值得在基准之前引入新的模型格式、分词器和包体。

漫画人脸或姿态也只能作为辅助：无人物、侧脸、夸张画风、局部特写和故意倒置都会
破坏它。除非后续错误分析显示“大量无文字横倒页都有人脸，且文字路线无法覆盖”，
否则不应优先投入。

### 明确暂不采用的路线

- **只继续调 `0.80/0.40/6/2` 阈值**：会直接过拟合当前少量样本。
- **只看图片长宽比或分镜线方向**：正常跨页与横倒单页不可分。
- **只要求当前模型四次旋转自洽**：只能验证等变性，不能验证语义正确。
- **只统计 OCR 字符数量**：识别存在不等于文字正立。
- **用章节多数硬覆盖所有单页**：会系统性误转封面、彩图和特殊构图。
- **把 Tesseract OSD 直接接入 Android**：它确实能输出 orientation、writing direction
  和 deskew 信息，见[Tesseract OSD API](https://tesseract-ocr.github.io/tessdoc/APIExample.html)，
  但此前漫画样本试验不稳定，且引入完整引擎的体积和维护成本不合算。
- **调用云端 VLM 判断**：网络延迟、隐私、离线阅读和成本都不适合逐页路径。
- **现在从头训练 CNN**：语料规模、作品多样性和标签质量都不足。

### 推荐实验顺序

1. 冻结当前实现，建立逐图结果表和按作品留出集。
2. 在同一离线入口上比较当前最强裁剪、median、trimmed mean、top-k 和多数投票。
3. 加入 ML Kit 文字框几何，先测它能否稳定给出文字轴向和有效 ROI。
4. 基准 `PP-LCNet_x0_25_textline_ori`，只测试文字行，不测试整页替换。
5. 测 `0°` 与当前候选的双方向 OCR；有区分度才扩展到四方向。
6. 将有效信号组成显式规则基线，再在样本足够后比较逻辑回归校准器。
7. 单页精度达标后再加入章节 HMM/Viterbi，并单列它改变了哪些页面。
8. 最后才移植最小胜出组合到 Android，测目标手机的冷/热 P50、P95、内存和功耗。

每一步都必须报告相对当前快照的正常页误旋转数、横倒页召回、unknown 数和耗时。
若复杂方案只提高训练/调试集而不提高按作品留出集，应直接回退，不进入 GitHub Actions
构建链路。

### P0：先建立可重复的离线基准

这是下一轮的第一步，优先级高于继续改算法。

1. 为所有 `landscape/` 图片补充准确的 `90°/180°/270°` 标签。
2. 按作品或卷划分调试集与留出集；留出集在方案确定前不参与阈值调整。
3. 写一个与 Android 预处理严格一致的基准入口，逐图导出：
   - 最终修正角度与接受/拒绝原因；
   - 四个旋转 × 五个裁剪的原始 logits；
   - 中文与日文字符数、element 数和置信度总分；
   - 解码、ONNX、OCR 和总耗时；
   - 冷启动/热启动、内存峰值。
4. 报告混淆矩阵，而不是只报告总准确率：
   - 正常页误旋转率（最重要）；
   - 横倒页召回率；
   - 接受覆盖率与拒绝率；
   - 接受样本中的方向准确率；
   - P50/P95 延迟。
5. 每张图片再做四方向旋转增强，验证同一图片的输出是否遵守旋转关系。

验收顺序应是：先把 `portrait/` 的误旋转压到可接受范围，再在这个约束下尽量提升
`landscape/` 的召回。不能通过放宽阈值换取表面上的正例提升。

### P1：改进当前信号的聚合方式

成本较低，适合先做消融实验：

- 不再使用单个最高分裁剪，尝试多数投票、截尾均值、中位数、至少 N 个裁剪同意，
  或 top-k margin 聚合。
- 同时取多个尺度，确认错误是否来自整页缩放后文字过小或网点混叠。
- 先用文字检测框定位气泡/文字区域，再对真实文字区域分类，避免人物或背景裁剪支配
  结果。
- 分别记录“内容方向模型一致性”和“文字区域一致性”，只有两个独立信号同意才旋转。
- 将固定阈值替换为在留出集上校准的拒绝规则；仍以高精度、低覆盖为目标。

### P2：让 OCR 提供方向证据，而不只是文字存在证据

可评估以下方法，但不能预设 ML Kit 一定能区分方向：

- 对 `0°/90°/180°/270°` 四个候选分别运行 OCR，比较有效字符数、element 数、平均
  置信度、行/块几何和识别稳定性。
- 只在某一个方向显著优于第二名时接受；四个方向接近时拒绝。
- 区分横排与竖排文本，避免把正常的日文竖排误当作横倒的横排文字。
- 单独评估中文模型对日文页面、日文模型对繁中页面的交叉响应，避免“中文先通过”
  掩盖更有用的日文方向证据。

此前观察到整页 ML Kit OCR 对旋转较鲁棒，因此这条路线必须先做离线实验。如果四个
方向的 OCR 分数没有稳定差异，应直接放弃，不能凭直觉接入。

### P3：评估更匹配任务的现成模型

不从头训练，先搜索和基准测试现成的移动端模型：

- 漫画/场景文字方向分类器，而不是证件文档方向分类器；
- 文字行方向模型，与页面级版式证据组合；
- 支持 4 方向并带有 unknown/reject 能力的轻量分类器；
- 可转换为 ONNX/TFLite、arm64 CPU 延迟和包体可接受的模型。

候选模型必须在相同留出集上与当前 6.5 MB ONNX 模型对比，包括 APK 增量、内存和
耗时。模型许可证、来源数据和可再分发性也必须记录。

若找不到合适的现成模型，可最后考虑在预训练视觉特征上做极小的校准层或轻量微调；
这不是从头训练，但也只有在样本量和按作品留出验证足够时才有意义，不应作为第一
选择。

### P4：利用章节上下文，但只作为弱先验

- 相邻扫描页往往共享扫描方向，可用前后页结果提高置信度。
- 章节上下文不能覆盖单页的强正向证据，否则会把封面、跨页或特殊构图一起误转。
- 可以要求连续两页独立提出同一旋转后才自动应用于低置信页；任何冲突仍保持 `0°`。
- 允许用户对单页手动纠正，并把纠正结果用于本地诊断或持久化覆盖，而不是静默改变
  全局阈值。

### P5：准确率稳定后再优化性能

- 根据早期裁剪结果做自适应退出，避免所有页面固定运行 20 次 ONNX。
- 比较 5 个裁剪小批处理与逐裁剪推理；动态 batch 可能更快，但要测 Android 峰值内存。
- 评估 NNAPI/XNNPACK 或 ONNX Runtime execution provider，必须以目标手机实测为准。
- 预取数量根据实际阅读速度和热耗动态调整，不要为了命中率持续占用 CPU。
- 保留当前页优先、取消旧预取、失败回退和双页拆分禁用缓存这些安全约束。

## 后续工作边界

下一轮开始时应先冻结当前提交并跑完整基准，不直接修改生产代码。每个候选方案都应
输出同一份结果表和失败样本列表，再决定是否替换当前实现。特别要检查：

- 新增 `portrait/` 中哪些页面被误旋转，以及错误发生在 ONNX 候选还是 OCR 门控。
- 新增 `landscape/` 中哪些页面被拒绝，以及是裁剪不一致、margin 不足还是 OCR 不足。
- 错误是否集中在某部作品、竖排文字、跨页或无对白页面。
- 修改是否只改善同作品相邻页；若是，应视为过拟合证据。

在上述证据齐全之前，当前实现应被视为实验性方案，而不是已经解决的通用漫画方向
检测器。


## 2026-08-21 第二轮：离线基准驱动的两处修改

本轮先按 P0 建立了桌面离线基准（`docs/orientation-bench/`，onnxruntime 复刻
Android 预处理，导出全部 4 旋转 × 5 裁剪 × 4 类原始分数），再在 43 张语料上
做失败模式分析，只落地了离线验证有收益的两处改动。

### 基准发现

1. **单最强裁剪门槛是主要漏判源**。17 张 landscape 中 9 张的四个旋转对齐类
   完全一致，但部分旋转置信度在 0.55–0.79 区间，被 `0.80/0.40` 单裁剪门槛
   整体否决；其中 139/142 两张四向证据完全一致。
2. **portrait 的误判候选是全裁剪一致的错**。11 张 portrait 页模型五个裁剪
   全部投同一错误类——换 median/top-k/majority 聚合救不了这类页，也压不掉
   landscape 漏判（离线对比数据见 `results/raw_scores.json` + evaluate.py）。
3. **OCR 门控确实挡不住“有字的正向页”**。Climax死靈法術18、芙兰05卷100 等
   portrait 页会被新候选直接放行，必须新增朝向证据。
4. **识别式极性判定无区分度**（方案 C 预警属实）：PaddleOCR 识别模型原生
   支持竖排文本，四方向识别质量几乎相同；墨迹投影极性同样旋转对称。
   本地无法客观判定 90° vs 270° 极性，landscape 目录标签存在噪声
   （03卷31、03卷81、06卷31 疑似本就正向，四路证据冲突）。

### 落地的修改

1. **分类聚合改为「四向等变一致 + 全局平均置信度 ≥ 0.75」**
   （`selectConsistentProposal` / `selectOrientationClass`）。不再使用单裁剪
   `0.80/0.40` 门槛。43 张回归：landscape 候选 2→5（含 6.jpg 的 180°，
   后被 OCR 门控正确拦截），portrait 候选不变。
2. **新增文字几何守卫**（`acceptOrGuard`）。ML Kit 行级 boundingBox 判断
   文字行轴向：横倒页在 0° 下不可能出现自信的竖长文字行；若中文+日文的
   竖排质量（字符数×置信度）≥ 3.0，说明页面本就竖排正立，拒绝 90/270
   候选并记 `geometry_guard_rejected`。43 张回归：portrait 误转候选 11→0。

### 已知代价与边界

- 几何守卫会同时拦下「存储正向但印刷文字为横排」的横倒页（如 landscape/2.jpg
  出版信息页）：其横排文字旋转后呈竖长框。按首要原则（误转代价高于漏判）
  接受该召回损失，此类页仍可手动旋转。
- 框形状长宽比分布无法区分「原生竖排对话列」与「横排文本旋转后」，守卫
  只能依赖轴向质量这一弱判据，阈值 3.0 未在留出集校准。
- 本地无 JDK/Android SDK，Kotlin 编译与单元测试由 GitHub Actions 承担；
  桌面基准脚本与原始分数保留在 `docs/orientation-bench/` 供下一轮复用。
